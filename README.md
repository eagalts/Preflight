# preflight.sh

Предполётная проверка сервера перед вводом в эксплуатацию.

Скрипт собирает «паспорт» машины (железо, ОС, CPU, память, сеть, диски), проверяет, годится ли она под гипервизор, и возвращает код выхода, по которому автоматизация (Ansible, AWX, Temporal-воркфлоу) может решить, идти дальше или остановиться.

Это первый шаг конвейера подготовки сервера:

```
сервер приехал → preflight.sh → установка ОС по сети → Proxmox → ввод в кластер
                     │
                     └─ FAIL → остановиться, завести заявку на железо
```

## Быстрый старт

```bash
chmod +x preflight.sh
./preflight.sh          # отчёт + проверки
echo $?                 # код выхода (см. ниже)
sudo ./preflight.sh     # от root дополнительно доступен серийный номер
```

## Что собирает

| Раздел | Данные | Источник |
|---|---|---|
| Система | hostname, тип машины (`vm` / `laptop` / `server` …), ОС, ядро, архитектура | `hostnamectl` |
| Виртуализация | гипервизор, если машина виртуальная | `hostnamectl` |
| Оборудование | вендор, модель, серийный номер | `hostnamectl` (серийник — только от root) |
| Uptime | время работы в минутах | `/proc/uptime` |
| CPU | логические CPU, модель, потоков на ядро, ядер на сокет, сокеты, тип аппаратной виртуализации | `lscpu` |
| Память | всего, доступно, swap | `/proc/meminfo`, `free -h` |
| Сеть | IP-адрес, через который уходит трафик наружу | `ip route get 8.8.8.8` (поле `src`) |
| Диски | имя, HDD/SSD, размер, пометка системного диска | `lsblk -dn`, `findmnt`, `lsblk -s` |

**Системный диск** определяется проходом по дереву устройств вверх: от того, что смонтировано в `/`, до устройства типа `disk`. Поэтому он находится и когда корень лежит прямо на разделе, и когда на LVM или RAID (`/dev/mapper/vg-root` → раздел → `sda`).

**«Логические CPU»**, а не «ядра»: `CPU(s)` в `lscpu` = сокеты × ядра × потоки. На сервере с Hyper-Threading это вдвое больше физических ядер.

## Проверки

| Проверка | Условие | Результат |
|---|---|---|
| Память | меньше 4 GiB | FAIL |
| Аппаратная виртуализация | нет флагов `vmx` (Intel) / `svm` (AMD) | FAIL |
| Сеть | нет ни одного интерфейса в состоянии UP, кроме `lo` | FAIL |
| Сеть | нет IP-адреса | WARN |
| Корневая ФС | заполнена больше чем на 90% | FAIL |
| Корневая ФС | заполнена больше чем на 80% | WARN |

Все проверки выполняются всегда, даже если одна из них упала: цель — получить полную картину за один прогон, а не чинить проблемы по одной.

## Коды выхода

Код выхода — **битовая маска** упавших проверок. Каждая проверка занимает свой бит, поэтому по одному числу видно все проблемы сразу.

| Код | Значение |
|---|---|
| `0` | всё в порядке |
| `1` | FAIL: память |
| `2` | FAIL: процессор не поддерживает виртуализацию |
| `4` | FAIL: сеть |
| `8` | FAIL: файловая система |
| сумма | несколько FAIL сразу, например `5` = память + сеть, `9` = память + ФС |
| `100` | FAIL нет, но есть хотя бы один WARN |

Разбор кода в другом скрипте:

```bash
./preflight.sh; rc=$?
(( rc == 0 ))   && echo "сервер готов"
(( rc == 100 )) && echo "есть предупреждения"
if (( rc > 0 && rc < 100 )); then
  (( rc & 1 )) && echo "проблема с памятью"
  (( rc & 2 )) && echo "нет аппаратной виртуализации"
  (( rc & 4 )) && echo "проблема с сетью"
  (( rc & 8 )) && echo "проблема с файловой системой"
fi
```

Почему маска, а не просто `0/1/2`: автоматизация получает не только «плохо», но и «что именно плохо», не разбирая текстовый вывод. Почему не «выходить на первой ошибке»: preflight должен показать все проблемы машины за один прогон. Код `100` выбран так, чтобы не пересекаться с маской (максимум 15) и с кодами bash (`126`, `127`, `128+N`).

## Требования

- `bash` 4+
- `systemd` (`hostnamectl`)
- `util-linux` (`lscpu`, `lsblk`, `findmnt`)
- `iproute2` (`ip`)
- `procps` (`free`)
- `coreutils` (`df`)

Работает без root; от root дополнительно доступен серийный номер оборудования.

Проверено на Debian 12 (VM в Proxmox/KVM).

## Как устроен скрипт

1. `set -euo pipefail` — строгий режим: скрипт падает на ошибке, на неизвестной переменной и на ошибке в любой части конвейера.
2. Функции сбора данных: `getHostnamectlInfo`, `cpu`, `getUptime`, `getRootDisk`, `printDisks`.
3. Сбор всех значений в переменные, затем вывод отчёта.
4. Функции проверок `checkRAM`, `checkVirt`, `checkNet`, `checkFS`: каждая печатает результат и добавляет свой бит в маску.
5. Сводка и `exit` с кодом по маске.

Где пустой результат — норма (например, у VM нет серийника, а без root его не видно вовсе), команды завершаются `|| true`, иначе `set -e` молча остановит скрипт.
